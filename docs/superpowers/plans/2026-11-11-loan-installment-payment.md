# Loan Installment Payment Implementation Plan

> **For agentic workers:** Use the existing implementation flow task-by-task. Do not create a branch or worktree. User instructions prohibit build, test, lint, and preview commands.

**Goal:** Let the user mark the oldest unpaid loan installment paid by recording a transfer from the installment schedule's saved wallet/bank into the loan.

**Architecture:** Extend loan payable data with its schedule source account. The account page submits an installment identity to a server action, which re-fetches current payables and creates a balanced transaction from authoritative source and amount data. Existing loan settlement then removes the paid amount from pending installments.

**Tech Stack:** SvelteKit forms/actions, Spring REST DTO, protobuf/gRPC, Go schedule and server layers, existing transaction endpoint.

**Spec:** `docs/superpowers/specs/2026-11-11-loan-installment-payment-design.md`

## Global Constraints

- No build, compile, test, lint, or preview commands; user runs these locally.
- Work on the currently checked-out branch; do not create branches/worktrees or commit.
- The transaction must be balanced: DEBIT loan and CREDIT the saved ASSET source account.
- Do not add a second paid-status source; loan ledger payments remain authoritative.

## Review Focus

- Payable source is absent for card bills: never show loan-payment controls for card bill rows.
- A stale or already-settled payable is submitted: the server re-fetch must reject it before creating a transaction.
- A schedule's wallet/bank differs from other accounts: use only its server-returned source account.
- Earlier unpaid installments exist: expose payment only for the oldest row across the loan, matching loan settlement order.
- Transaction creation fails: preserve the payable and show the error; do not mark it paid in the UI.
